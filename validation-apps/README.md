# Hermo consumer applications

Six independent applications exercise the **public, scoped Hermo REST and MCP interfaces**. They do not import Hermo server functions, read its database, or request target websites directly. The applications contain no sample success responses or seeded metrics.

Node.js 24 or newer is required. No additional packages or build step are needed. The lightweight browser modules use native HTML controls and a shared monochrome design system; this avoids six copies of a framework and keeps each consumer independently runnable.

## Start an application

Start the independent Hermo runtime first, using the main repository instructions. Then, from the repository directory, run one of:

| Application | Command | Default address |
| --- | --- | --- |
| Product Search Explorer | `node validation-apps/start.mjs product-search` | `http://127.0.0.1:4501` |
| Website Change Detector | `node validation-apps/start.mjs change-detector` | `http://127.0.0.1:4502` |
| Website-to-JSON Explorer | `node validation-apps/start.mjs json-explorer` | `http://127.0.0.1:4503` |
| Hermo MCP Tools | `node validation-apps/start.mjs mcp-tools` | `http://127.0.0.1:4504` |
| Website Records Dashboard | `node validation-apps/start.mjs website-dashboard` | `http://127.0.0.1:4505` |
| Hermo Reliability Lab | `node validation-apps/start.mjs reliability-lab` | `http://127.0.0.1:4506` |

For a different runtime or app port:

```powershell
node validation-apps/start.mjs product-search --runtime http://127.0.0.1:4336 --port 4510
```

Open the printed **127.0.0.1** address. Paste a published action endpoint (or its `/v1/actions/.../versions/1/runs` path) and the scoped key generated by Hermo. Select **Load published contract**, inspect its input/output schemas, enter matching input JSON, then run.

The configured runtime is the only forwarding destination. Pasting a URL does not change it: pass `--runtime` when starting the consumer host to select another local Hermo instance. Remote runtime URLs, private `/studio` routes, arbitrary proxy destinations and cross-origin browser requests are rejected.

API keys stay in the current browser tab's memory. They are never written to files or browser storage by these applications. Closing or reloading the consumer page clears the key. The change detector saves extracted observations, run IDs and verification evidence in this browser's local storage; it explicitly excludes keys. Treat exported website data and observations according to their sensitivity.

## Create the workflows

Use an isolated validation workspace for testing and preserve your existing Hermo workspace. Connect an authorized real website, create its workflow through Hermo, select dynamic navigation inputs and structured outputs, test against the website, and publish only a verified result. Public-site workflows must respect the target site's current rules. Do not assume another website has equivalent selectors or permissions.

The default app configuration expects these example **workflow contracts**, not hardcoded response data:

### Catalog workflow

- Published action: `validation.products`.
- Website: Books to Scrape, using its actual category navigation.
- Input: `category`, a string restricted to supported category path values such as `travel_2` and `mystery_3`.
- Navigate to the selected allowed category, wait for the product list, then extract its repeated product records.
- Outputs: `category`, `products` (an array of title, price, availability and absolute product URL), and optional structured metadata such as the actual page heading.
- Set relative selectors for repeated child fields and configure missing required fields to fail verification. Do not add a fictional search box: this target uses category navigation. The consumer's title filter operates on returned records.

### Quotes workflow

- Published action: `validation.quotes`.
- Website: Quotes to Scrape, using real page navigation.
- Input: `page`, a string restricted to supported page values such as `1` and `2`.
- Navigate to that allowed page, wait for the repeated quote elements, then extract their text, author and list of tags.
- Outputs: `page`, `quotes` (nested records with `text`, `author`, `tags` and optional source), and optional metadata from the actual website.

The product explorer, change detector and reliability lab default to the catalog workflow. The JSON explorer, MCP client and records dashboard default to quotes. Change the endpoint and JSON inputs to use a different compatible published workflow. Load its contract to discover the actual schema; the runtime remains the authority for input, permissions and output verification.

See the repository's `../docs/validation/real-world.md` for actual executed workflows, timestamps, revision/run IDs, failure cases and remaining acceptance limitations. A running UI alone is not live-site acceptance evidence.

## Application behavior

- **Product Search Explorer:** select a supported category, run, inspect actual product fields and raw JSON, then filter returned titles. Missing records do not produce fabricated products.
- **Website Change Detector:** make a verified observation; the next observation of the same workflow and inputs is classified as changed or unchanged using canonical structured output. Failed runs never replace a successful observation. Export timestamped local history as JSON. Unchanged public website data is a valid result.
- **Website-to-JSON Explorer:** navigate with the dynamic inputs, inspect repeated records, nested columns, optional absence and arrays, filter returned data, and export only the verified response with its run ID and evidence.
- **Hermo MCP Tools:** discover tools available to the current scoped key, inspect their schemas, invoke one or two concurrent authorized workflow calls, and poll `get_run` through `/mcp`. Discovery is refreshed before execution; browser execution remains serialized by Hermo. No language model is configured; this client does not pretend to generate AI answers.
- **Website Records Dashboard:** select a supported page, load its records and inspect details. The run shows its pinned revision and actual execution mode. Filters affect returned data; they do not pretend to execute a target-site search.
- **Hermo Reliability Lab:** use a budget of 1–6 requests, concurrency 1–2 and at least 1.5 seconds between admissions. Compare fresh request IDs with duplicate idempotency keys. Observe actual run IDs, revisions, queue wait, execution duration, failures and verification. Stop further admissions without misrepresenting already admitted runs as cancelled. Export measured results.

## Failure and lifecycle testing

Invalid keys, revoked keys, wrong workflow scope and server-side invalid inputs are ordinary observable failures. The reliability lab intentionally lets the runtime validate input so negative requests can be measured. Other apps preflight simple constraints from the published contract, and Hermo still performs authoritative validation.

Request timeouts never trigger an automatic workflow retry. If a run ID exists, inspect it in Hermo before retrying. **Cancel run** requests cancellation of that run; it cannot undo an action already submitted to a website.

Use managed local read-only workflows when verifying independence from the original browser:

1. Publish a compatible verified workflow in Managed Local Browser mode.
2. Open the consumer and enter its scoped key.
3. Close the Hermo dashboard, original website tab, companion popup and original Chrome browser.
4. Keep the Hermo runtime process and computer running.
5. Run the consumer. Verify a newly admitted run ID, actual website output, verification evidence and `managed_local` execution mode.

Connected Chrome is different: dashboard/popup closure is supported, but its authorized tab must remain available. Closing that tab must produce an accurate failure. Neither mode works after the independent runtime stops. A historical successful run is not proof of current browser health.

Test crashes, restart, cancellation and faults only with isolated Hermo-controlled resources. These consumer apps do not kill browsers, restart runtimes, edit workflow definitions or manage owner credentials. The repository's separate validation harness handles controlled fault scenarios and revision repair tests.

To check revision stability, edit a draft safely in Hermo, execute the consumer against the still-published revision, test and publish the draft, execute again, roll back in Hermo and execute once more. Compare the actual `workflow_revision` in each run. The consumer never mutates publication state.

## Tests

```powershell
node --test --test-concurrency=1 validation-apps/tests/*.test.mjs
```

The isolated regression suite covers all six app hosts, public-route boundaries, origin protection, secret forwarding, input validation, real protocol construction, polling, uncertainty, MCP errors, nested records, optional values, observation comparisons and bounded load. Its transport fixtures are explicitly identified; they are **not substitutes for live external acceptance**.

For machine-readable isolated test output:

```powershell
node --test --test-concurrency=1 --test-reporter=junit validation-apps/tests/*.test.mjs > work/consumer-unit-results.xml
```

Keep keys, passwords and local configuration out of source control and screenshots. The UI's generated cURL example always uses a placeholder key. Screenshots of successful states must be taken after actual execution, with the key input masked.

## Source structure

Each application's directory owns its `app.mjs` entry. `shared/client.mjs` contains only public REST/MCP calls, `shared/host.mjs` is the restricted loopback proxy/static host, `shared/ui.mjs` supplies accessible native controls/results, and `shared/data.mjs` contains record/observation/statistics logic. This shared consumer code is independent of Hermo's execution engine and can be reused without privileged runtime access.
