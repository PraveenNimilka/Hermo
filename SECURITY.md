# Security — Hermo local runtime

Scope: implementation boundaries and dated local validation for the early-access product, updated 16 October 2026. This is not an independent audit or penetration-test certification. Logged-out ChatGPT and Claude pages were checked in a disposable workspace; no real customer account or vendor login was used.

## Verified media previews — 15 October 2026

Published outputs may declare image/video/audio/file URL hints; these are schema
metadata, not executable instructions. URL conversion rejects credentials and
non-HTTP(S) values. The shared viewer uses DOM text and native media elements,
never result HTML, embedded documents or arbitrary scripts. Nested schema fields
retain the same typed extraction and verification rules.

Media hosts are contacted only after an explicit Load preview action. The viewer
accepts external HTTPS URLs, rejects obvious local/private literal hosts and
permits only public `/sandbox/` paths on its own runtime origin. This is a browser
preview check, not a DNS-rebinding-resistant server egress policy. No media proxy
or server download endpoint exists. Cross-origin previews use anonymous CORS and
no-referrer; no Hermo API key is forwarded or placed in links. Opening a direct
website link uses that browser's normal website session, subject to its policies.

The page CSP permits HTTPS image/media embedding while retaining same-origin
script/connect, no frames/objects and existing owner/consumer protections.
Preview errors do not retry website actions or fabricate a successful download.
Signed asset URLs can themselves be sensitive; they remain part of encrypted
run results and should be shared only intentionally. Previewing does not establish
asset persistence, ownership, provider entitlement or safety of a downloaded file.

## Trust boundaries and implemented protections

### Selected normal-Chrome tab

Website connections default to an explicitly selected normal-Chrome tab. Companion 0.7.0 requires Chrome 120+, and uses activeTab, scripting, storage, alarms, tabCapture and offscreen; its only permanent host permission is loopback. A background service worker polls local Hermo. Bounded tab grants and in-flight markers live in trusted chrome.storage.session, never storage.local. A recovery alarm restores an idle grant after worker suspension, subject to the same runtime lease. Unknown in-flight work disconnects without replay. No additional controller tab is opened in the default flow. No cookies, history or all-websites permission is requested; production has no CDP, debugger, fingerprint patch or verification solver.

Owner authentication, CSRF and explicit website/action authorization protect one-use ten-minute pairing codes. Codes are hashed in server memory and bound to owner, connection and exact website origin. Optional password confirmation remains compatible. The runtime credential remains in worker memory; the server stores only its hash. Only four exact companion POST/OPTIONS routes accept extension requests. Wrong-site pairing, replayed codes, unauthenticated replies and unsolicited command IDs fail. Restart, owner expiry, lock, Stop or lost transport ends active access; saved configuration remains. RPCs time out and detach without retrying uncertain actions.

Pairing immediately marks the authorized tab Connected. Private companion tabs no longer require or pin a detected account name/email. Runs use whichever account is currently signed in to the selected tab. A profile-name change therefore does not revoke keys or fail a run; this is an explicit product behavior change requested by the owner, not proof of vendor identity. Existing isolated private-browser replay and optional Google sign-in imports retain their identity checks.

Every command checks the selected tab ID, exact origin and scoped path. Local demo access remains restricted to /sandbox/, excluding Studio/private routes. Commands use registered local functions in Chrome's isolated world, not downloaded scripts. Detected sign-in/credential/challenge/refusal pages cannot record or return successful results. A sign-in failure leaves a still-live paired transport Connected so the owner can complete website sign-in and retry without pairing or confirmation. Leaving the approved origin, closing the tab, Stop or owner lock ends its live authority. Same-origin reload preserves an active connection.

The selected tab uses Chrome's own networking and profile storage. Recorded actions can change website data. Switching from isolated to selected-tab mode clears isolated state and invalidates affected verification/keys. Re-pairing an existing selected-tab connection preserves its recorded actions and scoped keys. Consumer keys remain workflow-scoped; source/readiness and selected output checks apply before a result is returned. Cancellation cannot undo a transmitted website submission. These checks cannot guarantee business truth, identify the vendor account cryptographically or force third-party acceptance.

Real Chrome tests use only new empty disposable profiles, synthetic website accounts and owned fixtures. They exercise actual popup/worker pairing, automatic UI completion, hidden-profile private tasks in all six action families, REST/MCP, focus without creating another browser, origin/path denial, sign-in failure and recovery, no credential/cookie export, Stop and owner lock. Personal provider sessions remain operator validation.

### Other integration boundaries

The provider-specific ChatGPT-plan connector was removed on 14 October 2026. Its OAuth callback, direct response endpoint, key authorization and setup/example pages are no longer available. Historical encrypted connector settings are retained without a runtime reader; removing source does not revoke an authorization already granted at an external provider. They are excluded from workspace exports as before. Recorded website ChatGPT/Claude tasks use the same approved browser action, verification and scoped `hm_live_` authorization as other website tasks. Google workspace sign-in remains independent and keeps its existing callback and owner checks.

Tests use synthetic OAuth identities, signing keys, streams and an owned consent fixture. Those historical protocol tests do not establish live provider acceptance, and the removed connector is not a current integration option. Google's automation refusal is explicitly recognized as `auth_rejected` and cannot be confirmed as a connection identity. No automated CAPTCHA solution, browser fingerprint disguise or silent cookie/profile attachment is introduced.

Responses use no-store, nosniff, restrictive CSP, frame-ancestor denial and permissions denial. Studio referrers are suppressed. The synthetic portal uses same-origin referrers to support browser form-origin checks. Passwords are prohibited in recorded actions; the separately confirmed browser session is encrypted. No screenshots or secrets are written to logs by the runtime. Studio screenshots are transient browser data and can show whatever the signed-in website displays.

Locking the workspace invalidates that owner session, discards unsaved recordings and closes Studio browser contexts. Consumer keys remain independently scoped and are not revoked by Lock. Closing the dashboard leaves runtime and companion authority intact. Explicit Lock ends companion links and active tab runs; isolated replay has separate consumer authorization. Disconnecting drops the saved session, revokes its keys and returns associated actions to draft. Pause/revoke/disconnect request abortion of matching active jobs. Already-transmitted traffic cannot be recalled.

## Core runtime reliability

One local runtime acquires an exclusive SQLite lock in its data directory before loading keys or recovering runs. The OS releases the lock after process death; a leftover lock database is not evidence of a live process. Local filesystem SQLite locking is required. This is single-process ownership, not a distributed lock.

Pairing codes are consumed and physical tab identities reserved before asynchronous browser closure. Tab uniqueness, owner lease and cancellation are checked again before installing a link. Pairing now requires the command_guard capability; an older companion is rejected with instructions to reload 0.7.0. Every mutation rechecks command authority after readiness, and the injected command checks its absolute deadline again. There is still an unavoidable boundary once a website submission has been issued.

Recording, pairing and accepted executions exclude conflicting owner mutations. The current queue is globally serialized, with a maximum of 30 active/queued runs. Abort causes are preserved; active interruption does not erase run provenance. Diagnostics record operations, variable names, timestamps, safe categories and output-failure reasons, never raw browser exceptions, selectors or input literals in step events. Existing encrypted owner input/result payloads remain private data, not automatically redacted data.

Active companion cancellation/timeout invalidates the live link, including pending command authority. Unstarted sibling requests fail as disconnected rather than being silently replayed or reported as cancelled. Explicit Stop cancels accepted work for that connection. A possible submission followed by transport loss, timeout, revocation or runtime interruption has an unknown external outcome; the original cause is retained and automatic retry is prohibited. API receipt reuse remains available after tab disconnection with a still-valid scoped key.

## Findings corrected during development

- Incorrect SQL placeholder counts blocked key creation and durable run admission; corrected and exercised by integration tests.
- Encoded, backslash, doubled-slash and traversal-like control-plane paths could bypass prefix-based guards; raw noncanonical paths now fail before routing.
- Proxy authentication lacked the 407 challenge expected by Chromium; corrected without loosening destination policies.
- The demo login's no-referrer response caused a null form origin; corrected only the demo response policy, retaining strict origin validation.
- SDK and static-serving dependency vulnerabilities were removed by updating versions; the dependency audit at that milestone found zero reported vulnerabilities. Recheck advisories for each release.
- MCP action names could collide with utility names; action tools now carry an `action_` prefix and each request has its own transport/server.
- Locking originally left Studio browser contexts alive; locking now closes them. Mobile UI now exposes the lock control.
- Supporting-domain failures were invisible. Diagnostics now expose only origin, resource type and reason; request queries/bodies are excluded. Origins require explicit approval, public DNS/IP validation and default HTTPS ports. Public websites cannot add the local sandbox as a dependency.
- Expanding origins revokes affected consumer keys, invalidates tested status and returns actions to draft. Active matching jobs are aborted; already-transmitted traffic cannot be recalled. Current Studio cookies remain in the same isolated context.
- Raw pointer/keyboard/navigation and unassociated control calls are rejected while recording to avoid silently missing workflow steps. Scrolling is permitted. Popup context timeouts and frame-navigation snapshot retries are bounded.
- Select/checkbox literal values are redacted from workflow exports, matching text-field export treatment. Parameter values and owner run exports may still contain private data.
- CONNECT-level failures now have per-context origin-only diagnostics, including redirected/preflight destinations that may be absent from page request events. Background connection entries remain visible for diagnosis but do not change page readiness unless observed or needed by the main navigation. All DNS results must remain public before any TCP connection; bounded fallback tries additional validated addresses, with IPv4 preferred.
- Failed navigation destinations are retained only in Studio memory for explicit retry; exposed addresses omit queries/fragments. Error, challenge and detected login pages have no selectable outputs and cannot be confirmed as accounts. Equivalent frame outputs are suppressed. These heuristics are not vendor authentication proof.
- Desktop handoff requires an authenticated owner, CSRF token and explicit action. It transfers in-memory cookies/IndexedDB into another isolated context while retaining the proxy, sandbox, allowed origins and download restrictions. Desktop handoff does not import regular browser profiles; the separately authorized normal-Chrome companion can import only reviewed Google cookies as described below. No fingerprint masking or challenge solver is present.
- Owner-session expiry/restart clears private UI state and returns to unlock automatically. Stale poll responses cannot overwrite the result of a newer browser operation.
- Dialog reopening can explicitly resume the same connection's active isolated context, preserving login progress in memory. Owner/CSRF checks still apply; workspace lock closes these contexts. After restart, only explicitly saved encrypted drafts or confirmed sessions are restored.
- Popup initial-navigation metadata is captured at BrowserContext scope and associated only through Playwright's actual frame/page identity. Unassigned navigation metadata is bounded to 32 requests in memory; exposed tab addresses still omit queries and fragments. Retrying or resuming synchronizes only persisted, previously approved origins. Permission additions still require the existing authenticated, CSRF-protected approval flow and invalidate published access.
- Proxy socket error handling exists from acceptance, including denied CONNECT and aborted local HTTP requests. Connection resets close the affected transport; they do not trigger request replay or relax egress policy.

## Operation and retention

### Google identity and public sources

Private Google browser profiles are separate from the workspace OAuth identity. Owner/CSRF-protected routes save only a selected ready, top-level Google account email marker and an authenticated-looking session; this is a user-selected marker, not cryptographic vendor identity proof. Reusable cookies are filtered by correct domain boundaries to reviewed Google hosts; origin storage is filtered by exact origin. Profiles are encrypted, capped at five and 2 MB each, and excluded from exports, logs and audit payloads. Their responses expose metadata only. Applying a profile requires explicit authorization, public-IP validation of the fixed Google origins and no active recording, creates a draft session, closes the previous Studio context, and revokes affected keys/actions/jobs. Confirmed replay state is not silently replaced. Public sessions cannot import or save profiles. Removing a profile clears the stored profile and dependent connection states and revokes keys; it does not revoke Google sessions on other devices. Saving/restoring uses cookies, local storage and IndexedDB, not the everyday Chrome profile or Chrome Sync. Signed-in Google sessions may expire or be rejected by providers; no automation concealment or CAPTCHA solver is present.

The earlier isolated-browser milestone removed its automatic screenshot timer: isolated captures are explicit or follow a Hermo interaction. Connected Chrome now refreshes detected fields while its owner panel is open; companion 0.7.0 additionally supports explicitly enabled visual sharing, with the capture lease and freshness rules described below. Each owner-authenticated preview read reconciles the active browser policy against that connection's persisted exact origins; unchanged permissions do not reset capture state. This does not authorize new origins or relax private-IP, proxy, CSRF, retrieval-method or account-confirmation protections. Preview-capture failures are reported separately from actual browser closure.

### Normal-Chrome companion boundary

Google may reject sign-in from automation-controlled browsers. A separate normal browser launcher uses a dedicated Chromium-managed profile inside the local data directory; its arguments contain no Playwright, CDP, headless, automation concealment, proxy or extension-loading flags. Its subprocess receives a minimal OS environment without Hermo master keys or OAuth secrets. It requests an interactive window only after an authenticated owner action. Normal Chrome uses ordinary browser networking and Chrome-managed profile files, not Hermo's policy proxy or database encryption. Workspace lock invalidates import authorization but does not close normal Chrome or erase its Google cookies.

The Manifest V3 companion has no background/content scripts or remote services. Google host and cookie permissions are optional and requested on explicit transfer; loopback is its only network destination. Google cookies can include multiple Google accounts signed into that Chrome profile, so the UI requires a dedicated profile. Tokens/cookies are not written to extension storage. A transfer code is generated only with owner authentication, CSRF, password confirmation and explicit authorization, bound to the current owner session, stored only as a hash in memory, expires in ten minutes and is consumed once. Lock/logout/session expiry/restart makes it unusable. A new code supersedes the owner's previous code.

Only `/companion/google/import` accepts a narrow cross-origin extension request. Chrome extension origins/IDs are validated; foreign website origins, invalid Host and cross-site website requests remain rejected. Privileged extension requests can omit Origin; they still require the unguessable owner-bound capability, valid extension ID and compatible Fetch Metadata. The supplied extension's fetch omits cookies, disallows redirects, has a timeout and accepts only canonical `http://127.0.0.1` workspace addresses. No CORS access or capability exemption is granted to Studio/private APIs. This does not authenticate software on the same OS account; local process compromise remains outside this threat boundary.

Import accepts at most 100 structurally valid, unexpired cookies from reviewed Google domains, rejects lookalikes, non-Google cookies, duplicates, control characters, invalid cookie prefixes/SameSite and oversized bodies. It copies cookies only, creates an encrypted draft profile/connection atomically, does not confirm vendor identity or replace published replay state, and never returns cookie values. Removal uses the existing dependent-session/key revocation path. Google cookies do not grant vendor API credits; providers can reject imported sessions or require new verification. Native Chrome launch and real extension installation/provider acceptance need operator validation. Automated tests use a synthetic launcher and synthetic cookie API; they do not certify successful real Google authentication.

Google workspace sign-in uses the server-side authorization-code flow in a normal top-level browser. The `/oauth/google/callback` route accepts a cross-site GET and requires an unexpired, one-use state bound to a HttpOnly SameSite=Lax browser cookie. All Studio mutations, including starting OAuth, retain CSRF protection. Linking or unlinking also requires the existing owner password; relinking revokes existing Google-authenticated sessions. Login compares the signed immutable Google `sub` to the encrypted linked owner. JOSE validates RS256 signatures from Google's fixed JWKS endpoint, issuer, audience, expiration, recent issuance, nonce and verified-email claims. PKCE binds code exchange; token requests have a timeout and disallow redirects. Tokens are never persisted or exposed. The OAuth client secret can be supplied through the server environment or saved encrypted locally through the owner/CSRF/password-protected Privacy form. Saved configuration takes precedence, is excluded from exports/status/audit data, and survives restart. Updating the client invalidates pending OAuth flows and Google-authenticated sessions. Secrets are excluded from browser subprocess environments. Unlinking removes the Google owner identity; client configuration remains available for relinking. Password recovery remains available. Starting from a localhost alias is rejected to avoid cross-host cookie binding errors. Workspace and OAuth cookie names include the port so the separate demo instance does not overwrite the main workspace session. This does not establish a security boundary against hostile software on the same device; browser cookies are host-scoped.

The public SPA landing page at exactly `/` also accepts cross-site GET requests with browser Fetch Metadata mode `navigate` and destination `document`. Chrome retains cross-site metadata across the callback's redirect to `/` or `/#privacy`; rejecting the landing page otherwise breaks a successfully validated sign-in. This exception serves static HTML only, creates no session, returns no owner data and does not exempt Origin validation, host/path checks, POST, embeds, fetch requests, Studio or consumer APIs. Real Chromium tests use an owned cross-site localhost consent fixture to exercise linking, signed-out login and cancellation; actual Google token verification is tested separately with signed test tokens. References: [W3C redirect semantics](https://www.w3.org/TR/fetch-metadata/#redirects), [Google's public navigation policy guidance](https://web.dev/articles/fetch-metadata). Top-level cross-site GET document navigation is also permitted for the synthetic `/sandbox/` practice pages so extension-initiated navigation can exercise the owned fixture. This does not exempt Studio, consumer APIs, POSTs, invalid hosts/paths or foreign Origin headers; the sandbox contains only synthetic accounts/data.

Public connections use a distinct origin-based identity contract and always create anonymous replay contexts, ignoring saved account cookies and origin storage. Credential forms, challenges, errors and unexpected origins still fail. A lone Login link on a public page does not make that page an authentication form. Parameterized page reads substitute exactly one complete path segment, reject traversal/URL/query characters, require an approved public origin and reject redirected record URLs. The record verifier derives its output from the actual browser URL; it is not an echoed request value. These checks establish routing/output correlation, not the business truth of remote content.

The live website lab targets only the two ToScrape websites explicitly offered for automation practice. Its owner-only setup uses the ordinary connection/recording/test/publish APIs. Keys remain encrypted on the server and are never exposed to the demo browser. Both synthetic and public demo catalogs are private workspace data, excluded from packaging. Live OAuth is unverified until the operator creates their client and completes consent personally.

Run one process per data directory under a dedicated OS account on a trusted device. Keep the Chromium sandbox enabled and dependencies patched. Do not add a tunnel, change the host bind address, or deploy publicly without a separate authentication, transport, tenancy and isolated-runner design review. The remote API/OpenAPI URLs are loopback-only by design.

Completed run rows expire after 7, 30 or 90 days; audit metadata after 90 days. This is logical retention deletion, not guaranteed forensic erasure of SQLite pages, WALs, OS caches, backups or SSD storage. Workflow definitions and active connections persist until manually managed; disconnect removes the saved session from the current connection row. Exports contain private run data and are unencrypted downloads; protect them yourself.

The queue is serialized and durable. Interrupted active jobs become failed after a restart; they are not automatically replayed. Queued jobs resume only after key, publication, connection and version checks. Idempotency is an admission property tied to retained run records, not an external exactly-once guarantee. A failed response can follow already-transmitted website traffic.

## Scalar contract boundary

Scalar draft contracts are owner/CSRF protected, version checked and limited to metadata for already recorded fields. They cannot supply selectors, steps or new origin permissions. Saving invalidates test evidence; published/paused contracts are immutable through this endpoint. Both adapters retain raw verification before converting strict output types, and conversion failures omit successful results. Defaults are validated functional configuration exposed in schemas/documentation/exports, not a secret vault. Complete sensitive-input classification and redaction remains required before sensitive production use.

## Revisions, draft editing and managed targets

Published definitions and nonsecret execution policy are encrypted immutable revisions. SQLite rejects revision updates. Draft edits, restoration and target changes invalidate test evidence; publication checks the saved draft hash and exact tested connection configuration. Accepted runs persist a private snapshot before queueing, so later edits cannot change already authorized work. Current key revocation, connection status, origins and identity still apply at execution. Historical runs without revision provenance are not relabeled with invented evidence.

The owner-only ordered editor accepts a strict operation/locator schema, never arbitrary JavaScript. Locator ambiguity fails closed before issuing a browser mutation. Selecting another execution connection requires explicit authorization, same project, same website origin, compatible permissions and capability checks. Browser sessions are not transferred. Historical target references prevent deletion and cross-project movement that would invalidate revision isolation. Managed replay remains restricted to GET/HEAD, with its existing egress and sandbox-path checks; it is not a general background submission runtime.

Recursive extraction uses fixed repository-owned DOM code, bounded schemas and data, relative row/container selectors and explicit conversions. Missing required, invalid present or oversized values fail; no inferred or fabricated result is returned. New companion capabilities are negotiated. Old companions can execute compatible scalar workflows but cannot silently ignore unsupported waits or structured extraction. Output-node identities used for freshness stay private and are not exposed in run diagnostics.

The playground uses real consumer routes and a pasted workflow key held only in component memory. It does not use owner cookies to bypass key checks. Revision mismatch blocks a new admission; receipt recovery retains the original request and idempotency key. An uncertain external outcome is never retried automatically. Projects are local organization for one owner, not a multi-user security boundary.

## Required before sensitive production or hosted release

Independent code/security review; adversarial public-site testing in disposable OS isolation; CSP/XSS/SSRF and authentication fuzzing; selector/freshness benchmarks; stronger account identifiers; quotas and lifecycle limits; OS-enforced browser egress and file isolation; a reviewed HTTPS/OAuth tenancy layer if hosting; operational key rotation/recovery and tested encrypted backups. These are future requirements, not features shipped here.

No independent security audit or completed external review is claimed.


## Integration-lab and browser lifecycle additions

The three demo portals use synthetic credentials and independent HttpOnly cookies. Owner-only lab setup uses the ordinary recording, confirmation, testing and publication routes. Its catalog is encrypted; consumer key secrets are never returned to the lab browser or stored in browser storage. Lab result polling uses the same key ownership checks and quotas as other consumers. Setup requires explicit authorization and a valid CSRF token; locking the workspace denies subsequent owner calls. Rebuild rotates and revokes previous lab keys.

Preview captures are deduplicated. Desktop transfer waits for a pending capture and keeps the previous context if creating the replacement fails. Closed contexts can be reopened only by the authenticated owner. This preserves policy enforcement and account isolation; it does not certify a provider’s human-verification step.

Automated tests and dependency advisory checks are project validation, not independent security certification or a guarantee of zero vulnerabilities.

## Selected-tab visual sharing (companion 0.7.0)

Visual sharing requires the owner's explicit **Enable live preview** action from the companion popup on an already paired website tab. New tabCapture/offscreen permissions add no website host grants. Video only; no audio, desktop-wide capture, debugger, cookie access, recorded video, or persistent frame cache. A hidden extension document samples bounded JPEG frames on authenticated owner requests; generated workflow keys have no preview or arbitrary capture route.

Frames are accepted only while the tab URL still matches its authorized origin/path, with safe page inspection before and after capture. Credentials, verification, denied pages and stale frames are suppressed. No images are added to workflow runs or logs. Scope exit, closure, stop, disconnect and expiry end capture. The offscreen document independently enforces a 15-minute maximum (capped by the owner lease) and a two-minute idle limit. MV3 recovery closes orphan capture instead of resuming it. The browser compositor remains alive during authorized sharing, even between frame requests; Stop preview ends that access without cancelling workflows.
