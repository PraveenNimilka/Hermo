Connect Google.
Keep your space private.

This enables Google sign-in for Hermo. It does not sign the isolated automation browser into other websites. Each website needs its own supported login.

1. Create a Google Cloud project

Open Google Cloud Console in your normal Chrome or Edge browser. Create or select your own project. Open Google Auth Platform.

Under Branding, set the app name to Hermo, your support email and developer contact email. Under Audience, choose External for a personal Gmail account, keep the app in Testing, and add your own Google email as a test user. A Workspace organization can use Internal where eligible.

2. Register a Web application client

Under Clients, create an OAuth client with application type Web application. Name it Hermo Local. Use only basic OpenID scopes: openid email profile. No Gmail, Drive or other account-data scopes are needed.

Add an Authorized redirect URI that exactly matches the server you use:

http://127.0.0.1:4318/oauth/google/callback

For a different port, replace 4318. Hermo’s Privacy page shows the exact URI. Keep the host as 127.0.0.1, with no trailing slash. Authorized JavaScript origins are not needed for this server-side authorization-code flow.

3. Save the client privately in Hermo

Open Hermo in normal Chrome or Edge at http://127.0.0.1:4318, unlock with your existing workspace password and open Privacy. Enter the client ID and client secret into the Google configuration form. Confirm your workspace password and choose Save Google configuration.

The secret is encrypted locally, hidden in the form, excluded from exports and never shown again. No server restart is required. If a secret was shared in a screenshot or message, open Google Auth Platform → Clients → your client → Add Secret. Copy the replacement privately and Disable the exposed old secret before saving the replacement here. Creating a new secret alone does not disable the old one. See Google’s secret rotation instructions.

Alternative: server environment configuration

Use this method instead if you prefer not to save the client in Hermo. Saved local configuration takes precedence over environment values. In PowerShell, change to your Hermo project directory. Run these commands, then enter your own values at the prompts. The secret prompt hides your input and keeps its value out of command history:

$env:HERMO_GOOGLE_CLIENT_ID = Read-Host 'Google client ID'
$hermoGoogleSecret = Read-Host 'Google client secret' -AsSecureString
$env:HERMO_GOOGLE_CLIENT_SECRET = [System.Net.NetworkCredential]::new('', $hermoGoogleSecret).Password
$hermoGoogleSecret.Dispose()
Remove-Variable hermoGoogleSecret
$env:HERMO_PORT = '4318'
npm.cmd start

If Hermo is already running, stop its server first. These variables apply to this terminal session. Use your OS credential manager or private service configuration for persistent secrets. Do not put the client secret in a shared script. When you finish, stop Hermo and close this terminal session.

4. Link your account once

Open http://127.0.0.1:4318 in normal Chrome or Edge. Unlock using your existing workspace password. Open Privacy, enter your workspace password again and choose Link Google account. Select the test-user account and approve basic identity access on Google’s own page.

You return to Hermo with the verified account linked. After locking the workspace, Continue with Google can unlock it. Your workspace password remains available for recovery. Unlinking requires that password.

If Google refuses the request

redirect_uri_mismatch: match scheme, 127.0.0.1 host, port and path exactly. access_denied: add the selected account under Audience → Test users. Sign-in expired: start again from the same normal browser. Google not configured: set both variables in the server’s terminal and restart it. Embedded browser blocked: authorize in normal Chrome or Edge, outside Hermo’s website preview.

Google authorization cannot create a universal browser login or guarantee that another provider accepts automation. Complete website MFA and verification yourself in its supported flow.

References: Google’s web-server OAuth guide and OAuth policies.

No Google access or refresh tokens are stored. Your linked identity is encrypted locally.
